🤖 Autonomía: los agentes trabajan 24/7

La ventaja más inmediata de la ingeniería de loops es la autonomía: una vez configurado, el sistema sigue trabajando sin que el humano tenga que estar frente a la terminal. El ciclo activa al agente, el agente ejecuta y valida, y el ciclo programa la siguiente iteración. El humano duerme, el agente trabaja.

💬 Qué significa en la práctica

"Configuramos Claude para que se active por sí mismo cada cinco minutos. Por supuesto, puedes ajustar ese intervalo. Buscará entradas en un sistema externo, como GitHub, por ejemplo. Mientras nuestra terminal esté abierta y Claude Code esté en ejecución, podrá encargarse de esto de forma autónoma."
— Cole Medin

Imagina un escenario real: tienes 20 issues abiertas en GitHub. En vez de resolverlas una por una sentado en tu escritorio, configuras el orquestador con la especificación, defines los criterios de validación y te vas a dormir. Al despertar, el sistema procesó 15 de las 20 issues, creó PRs y está esperando tu revisión de las 5 que tuvieron problemas de validación.

⏰ Escenarios donde la autonomía brilla

  • ✓Mantenimiento nocturno: resolver issues de baja prioridad durante la madrugada
  • ✓Monitoreo continuo: revisar repositorios para encontrar nuevas issues cada X minutos
  • ✓Procesamiento del backlog: abordar un conjunto de tareas acumuladas en un lote
  • ✓Revisión automatizada: revisión preliminar de código en PRs mientras el equipo duerme

📈 Escala: paralelismo con worktrees

La segunda gran ventaja es la escalabilidad horizontal. En lugar de procesar tareas secuencialmente, el orchestrator puede despachar varios workers para que se ejecuten en paralelo, cada uno en un worktree de git aislado. El rendimiento de desarrollo se multiplica.

"Podemos usar Archon para poner en marcha workflows en paralelo y gestionar varios issues de GitHub exactamente al mismo tiempo. [...] Aquí tenemos nuestro Cloud Code iniciando cuatro workflows para gestionar issues de GitHub."
— Cole Medin

✓ Con paralelismo

  • ✓4 issues resueltos al mismo tiempo
  • ✓Cada worker en su worktree aislado
  • ✓Branches de bases de datos de Neon para el aislamiento de datos
  • ✓Merge controlado por el orchestrator

✗ Sin paralelismo

  • ✗1 issue a la vez, de forma secuencial
  • ✗Tiempo total = suma de todas las tareas
  • ✗El humano queda bloqueado hasta que termine
  • ✗Sin aprovechamiento de recursos ociosos

Cole demuestra que, en su enfoque con Archon, el orchestrator principal lanza 4 workflows de corrección, verifica que se hayan creado los PR y luego lanza 4 workflows de revisión de código. Son más de 9 sesiones de agentes trabajando coordinadamente, pero cada una es "lean" y está enfocada en su tarea.

🧱 Componibilidad: sistema modular

La arquitectura orchestrator-workers es naturalmente modular. Cada componente tiene una responsabilidad clara y puede cambiarse de forma independiente. El orchestrator puede usar un modelo distinto al de los workers. Los workers pueden usar modelos distintos entre sí. El state store puede ser Postgres, SQLite o cualquier otra base de datos.

"En cada nodo de este flujo de trabajo de Archon, puedo decidir qué modelo voy a usar. [...] Podemos usar Claude Code para la implementación. Luego podemos usar Codex para la revisión. Y para cargar todo nuestro contexto y explorar al principio, podemos usar un modelo más pequeño, como Kimi K 2.7."
— Cole Medin

🧩 Ejemplo de combinación de modelos

1

Clasificar (triaje)

Modelo pequeño y económico (Haiku, Kimi K 2.7). Decide si el issue es un error o una funcionalidad. No necesita un razonamiento profundo.

2

Research (exploración)

Modelo intermedio para explorar el codebase y entender el contexto. Buena capacidad de lectura, costo moderado.

3

Implement (código)

Modelo potente (Claude Sonnet/Opus). Aquí es donde el razonamiento de verdad importa: escribir código y resolver errores.

4

Review (validación)

Otro modelo (Codex, o el mismo del implementador). Verifica si el código es correcto, si las pruebas pasan y si el PR está listo.

💡 Exploración y prueba de concepto

Cole Medin identifica un caso de uso en el que el loop engineering funciona particularmente bien: exploración y pruebas de concepto. Cuando el objetivo no es entregar código de producción, sino validar una hipótesis, probar un enfoque o crear un prototipo rápidamente, los loops son herramientas poderosas.

"Para crear pruebas de concepto y explorar ideas, creo que es muy bueno. Pero no es como si quisiera hacer toda mi programación con IA usando esto."
— Cole Medin

📝 Exploración práctica

Cole lo demostró en el dashboard que construyó: "I just have been going through a lot of really simple examples, but like non-trivial enough where it does have to go through quite a few rounds to build it. So like building a single page Kanban board as a static web app." El agente exploró, iteró y produjo un prototipo funcional en rounds automatizados.

Para explorar, el costo elevado es aceptable porque el objetivo es aprender, no entregar. Si el PoC funciona, lo perfeccionas manualmente. Si no funciona, lo descartas y pruebas otro enfoque. Los loops aceleran este ciclo de prueba y error.

🏋 Incrementalidad: ciclos pequeños

Un principio central de Loop Engineering es que las tareas grandes deben dividirse en ciclos pequeños. En lugar de pedirle al agente que construya una app entera de una vez, el loop garantiza que haga una tarea por iteración, la valide y solo entonces avance a la siguiente.

"Nunca queremos que un agente de programación intente encargarse de demasiadas cosas a la vez, o se verá completamente abrumado."
— Cole Medin

🔄 Cómo funciona la incrementalidad

Ronda 1: Tarea 1

El agente toma la primera tarea de plan.md, la ejecuta, la valida (¿pasan las pruebas?) y la marca como completada. El loop programa el siguiente wake-up.

Ronda 2: Tarea 2

El agente se activa, lee el state (la tarea 1 está done), toma la tarea 2, la ejecuta y la valida. El contexto está fresco porque cada round puede ser una sesión nueva.

Ronda N: Conclusión

Cuando todas las tareas están marcadas como done, el loop detecta que se alcanzó el goal y se detiene. El orchestrator informa el resultado final a la persona.

🎯 Punto de reflexión

La incrementalidad es la defensa natural contra dos problemas: la sobrecarga de contexto (cada ronda puede tener contexto nuevo) y las alucinaciones acumuladas (la validación entre rondas detecta errores temprano). Es el principio que hace que los ciclos funcionen en vez de ser una apuesta a ciegas.

❓ Preguntas

Las ventajas son reales, pero deben evaluarse con honestidad. Cada beneficio tiene un costo o una condición que debe cumplirse.

La autonomía exige confianza en el harness

Dejar agentes ejecutándose sin supervisión solo funciona si el harness es robusto. Sin observabilidad, seguimiento de costos y puntos de validación, la autonomía se convierte en negligencia. Cole no ejecuta loops a ciegas: «we can always have it pause for us to validate something before it continues.»

La escala multiplica el costo, no solo el throughput

4 workers en paralelo resuelven 4 issues más rápido, pero también consumen 4 veces más tokens. Si cada issue cuesta $5 en tokens, 4 en paralelo cuestan $20. La escala es una ventaja real, pero es costosa. El ROI depende del valor de las tareas que se automatizan.

La componibilidad exige un trabajo de ingeniería considerable

Armar un sistema con una combinación de modelos, state store, worktrees y validation gates no es trivial. La composabilidad es una ventaja de la arquitectura, no una ventaja que se materializa por sí sola. Alguien tiene que construir y mantener el harness.

🤔 Punto de reflexión

Cole resume: "Me gusta el concepto y quiero impulsar la autonomía de mis agentes de programación, pero necesitas el sistema adecuado. De lo contrario, todo se va a desmoronar por completo." Las ventajas existen, pero dependen de ciertas condiciones. El siguiente módulo (2.2) mostrará qué pasa cuando no se cumplen.
