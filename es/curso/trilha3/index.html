🔄 Loop básico con Claude Code

Configuración de la skill /loop, creación de plan.md, prompt para que el orchestrator configure el loop, demo con una lista de tareas secuencial y activación automática.

Qué es:

Claude Code tiene una capacidad integrada llamada "loop skill" que enseña al agente a configurar loops automáticamente.

Por qué aprender:

Es el punto de partida más sencillo para loop engineering. Un solo prompt carga todo el sistema.

Conceptos clave:

La skill de loop como capacidad. Prompt inicial. Autoconfiguración por parte del agente.

Qué es:

Un documento Markdown con tareas numeradas que el agente procesa una por una, marcando cada una como completada.

Por qué aprender:

La calidad del plan.md determina la calidad del resultado. Tareas bien definidas = mejores resultados.

Conceptos clave:

Granularidad ideal. Criterio de aceptación por tarea. Orden secuencial o paralelo.

Qué es:

El prompt que carga la skill de loop e indica al agente que procese el plan.md. El agente configura /loop por su cuenta.

Por qué aprender:

Un buen prompt inicial marca la diferencia entre un loop funcional y uno caótico.

Conceptos clave:

"Carga la skill de loop". Configuración automática de /loop. El prompt como sistema, no como instrucción.

Qué es:

El agente completa una tarea, programa el siguiente wake-up mediante /loop y continúa hasta completar todas las tareas de plan.md.

Por qué aprender:

Ver el flujo real ayuda a entender cómo se conectan los primitivos en la práctica.

Conceptos clave:

Ciclo de wake-up. Validación entre tareas. Prompt generado automáticamente por el agente.

Qué es:

Colección de prompts listos para copiar para los escenarios más comunes: task runner, revisión de código y exploración.

Por qué aprender:

Empezar con prompts probados acelera la adopción y evita errores comunes de configuración.

Conceptos clave:

Plantillas reutilizables. Parámetros ajustables. Adaptación según el contexto.

Qué es:

El loop básico se ejecuta en una sola sesión, usa un solo modelo y no tiene un state externo. Esto limita la escalabilidad y la confiabilidad.

Por qué aprender:

Entender las limitaciones motiva la búsqueda de soluciones más sólidas en los siguientes módulos.

Conceptos clave:

Una sola sesión = exceso de contexto. Un solo modelo = costo alto. Sin state = sin durabilidad.

3.2 ~40 min

⚙ Workflows deterministas con Archon

El harness builder de Cole Medin: workflows donde la persona define el proceso, una combinación de modelos por step y durabilidad con Postgres/Neon.

Qué es:

Archon es la herramienta de Cole Medin para orquestar sesiones de coding agents con workflows definidos por personas.

Por qué aprender:

Representa el enfoque opuesto al loop puro: la persona define el proceso, no el agente.

Conceptos clave:

Harness frente a loop. Archivo de workflow. Pasos deterministas. Combinación de proveedores.

Qué es:

Pipeline determinista: extraer el issue, buscar contexto, clasificar el tipo, investigar, implementar, validar y crear un PR.

Por qué aprender:

Es el ejemplo más práctico de cómo combinar determinismo con LLM, usando el agente solo donde realmente hace falta.

Conceptos clave:

Pipeline como grafo. Pasos deterministas frente a pasos impulsados por LLM. Clasificación como decisión sencilla.

Qué es:

En el enfoque determinista, la persona define qué steps existen y en qué orden. En el loop puro, el agente decide todo por su cuenta.

Por qué aprender:

Entender ese trade-off es fundamental para elegir el enfoque adecuado para cada escenario.

Conceptos clave:

Confiabilidad frente a flexibilidad. El agente como ejecutor, no como quien toma las decisiones.

Qué es:

Cada nodo del workflow puede usar un modelo diferente. Los pasos sencillos usan modelos económicos; los pasos críticos usan modelos potentes.

Por qué aprender:

Es la principal palanca para optimizar costos en workflows autónomos.

Conceptos clave:

Enrutamiento de modelos. Costo por paso. Combinación de proveedores. Kimi para explorar, Claude para implementar.

Qué es:

Los registros, las ejecuciones y las conversaciones se guardan en Postgres/Neon. Si la máquina falla, el flujo de trabajo se reanuda desde el paso exacto.

Por qué aprender:

La durabilidad es lo que transforma un experimento en un sistema confiable.

Conceptos clave:

Almacén de estado. Reanudar desde el paso. Neon branching para workers paralelos.

Qué es:

Prompts optimizados para cada step: clasificación, investigación, implementación, validación y code review.

Por qué aprender:

Los prompts listos ahorran tiempo y sirven como base para adaptarlos a tu contexto.

Conceptos clave:

Plantilla por paso. Markdown como contexto. Transferencia entre pasos mediante documentos.

3.3 ~35 min

📊 Panel de control (Agent Control Plane)

Observabilidad en tiempo real: ver las decisiones del orchestrator, el cost tracking, human-in-the-loop y el deploy remoto.

Qué es:

Dashboard open source que Cole construyó para gestionar loops con durabilidad, observabilidad y human-in-the-loop.

Por qué aprender:

Sin control visual, los loops son cajas negras que queman tokens sin feedback.

Conceptos clave:

Dashboard como sistema nervioso. Open source en GitHub. Backend con Pi/Kimi.

Qué es:

Todos los loops, eventos y logs se guardan en Postgres (a través de Neon) para garantizar durabilidad y analytics.

Por qué aprender:

El state externo permite reanudar loops después de crashes y analizar históricamente los patrones de ejecución.

Conceptos clave:

El orchestrator lee el state del banco. Los workers actualizan el state en el banco. El banco como fuente de verdad.

Qué es:

Ver en tiempo real qué decisiones toma el orchestrator, cuántos workers activa y el progreso de cada round.

Por qué aprender:

Poder ver y entender las decisiones del orchestrator es esencial para depurar y mejorar el loop.

Conceptos clave:

Decision log. Historial de rondas. Seguimiento del dispatch de workers. Event stream.

Qué es:

Métricas de tokens consumidos por ronda, por worker y costo total del run. Visibles en el dashboard.

Por qué aprender:

Sin seguimiento de costos, es imposible optimizar. El dashboard mostró más de 1M de tokens para una app sencilla.

Conceptos clave:

Tokens por ronda. Costo del orchestrator frente a los workers. Desglose por modelo.

Qué es:

El loop puede pausarse después de cada ronda y esperar la aprobación de una persona antes de continuar.

Por qué aprender:

HITL es la salvaguarda esencial que evita el problema de «ejecutar durante un día y volver para encontrar un desastre».

Conceptos clave:

Pausa entre rondas. Flujo de aprobación/rechazo. Grupos de permisos. Verificación de identidad.

Qué es:

El dashboard se puede deployar en la nube mediante Retool, lo que permite el acceso remoto y compartirlo con el equipo.

Por qué aprender:

El deploy remoto transforma una herramienta local en infraestructura de equipo.

Conceptos clave:

Importación de React a Retool. Conexión con Neon. Grupos de permisos. Registros de auditoría.

💰 Optimización de costos

Combinación de proveedores, enrutamiento de modelos, estado externo, worktrees y métricas para mantener loops financieramente viables.

Qué es:

Usar distintos providers para distintos roles: modelos económicos para la orquestación, modelos potentes para la implementación.

Por qué aprender:

Es la principal palanca para reducir costos sin sacrificar la calidad del resultado final.

Conceptos clave:

Pi/Kimi como orchestrator económico. Claude Code para la ejecución. Codex para la revisión.

Qué es:

Enruta tareas a modelos según su complejidad: una clasificación simple usa Haiku; una implementación compleja usa Claude.

Por qué aprender:

Cada token cuenta. Usar Opus para clasificar un error o una funcionalidad es un desperdicio.

Conceptos clave:

Enrutamiento basado en la complejidad. Costo por token según el modelo. Decisiones simples frente a complejas.

Qué es:

Mantener el estado en una base de datos externa en lugar de acumularlo en la ventana de contexto del LLM. Cada sesión empieza limpia y lee el estado.

Por qué aprender:

Context bloat es la causa #1 del deterioro en loops largos. El estado externo lo resuelve.

Conceptos clave:

Ventana de contexto como caché. Base de datos como almacenamiento. Sesión sin estado. Ciclo de lectura-ejecución-escritura.

Qué es:

Git worktrees crean copias aisladas del repo para que N agentes trabajen en paralelo sin conflictos de código.

Por qué aprender:

El paralelismo real requiere aislamiento real. Los worktrees son el mecanismo más práctico para esto.

Conceptos clave:

Una worktree por worker. Una rama por tarea. Merge después de la validación. Evita conflictos de puertos.

Qué es:

Batch: acumular tareas y procesarlas de una vez (más barato). Real-time: procesarlas de inmediato (más ágil).

Por qué aprender:

Elegir el modo equivocado desperdicia dinero o tiempo. El contexto determina la elección.

Conceptos clave:

Batch para issues de GitHub durante la noche. Real-time para correcciones urgentes. Trade-off entre latencia y costo.

Qué es:

Las tres métricas esenciales: tokens consumidos por tarea, costo por round del orchestrator y tasa de éxito de los workers.

Por qué aprender:

Lo que no se mide no se puede optimizar. Estas métricas son lo mínimo para evitar desperdicios.

Conceptos clave:

Tokens/task como KPI. Costo por ronda. Tasa de éxito. Análisis de tendencias. Alertas de presupuesto.
